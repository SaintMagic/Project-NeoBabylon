# NeoBabylon documentation

The documentation is organized by subject and status. Each subject should
have one canonical document; links elsewhere should point to it instead of
creating parallel summaries.

## Authority and status

1. Martin's explicit accepted requirements and decisions.
2. Verified behavior of the pinned Codex source and matching binaries.
3. The versioned reference corpus in `reference/`.
4. Accepted decision records and release verification.
5. Product and architecture documents.
6. Roadmaps, build plans, and WIP notes.

Use these labels consistently:

- **Accepted** — an explicit product requirement or reviewed decision.
- **Observed** — verified in the pinned source, docs, or binary.
- **Proposed** — a recommendation awaiting review or implementation approval.
- **Experimental** — upstream or NeoBabylon behavior whose stability is not
  established.
- **Open** — a decision or evidence gap that needs resolution.
- **Deferred** — intentionally outside the current phase.

## Categories

- `product/` — product intent, capability coverage, roadmap, and status.
- `architecture/` — system boundaries, provider model, tool strategy,
  upstream ownership, and the canonical Codex-first UI/UX reference.
- `decisions/` — dated choices and their evidence.
- `guides/` — contributor and development guidance.
- `release/` — verification, legal, and distribution evidence.
- `history/` — preserved startup brief and dated implementation records.
- `WIP/` — build plan and unresolved questions; proposals remain distinct
  from accepted requirements.

The structure is inspired by the live CanonWell documentation layout only.
CanonWell's domain, release, storage, and platform rules are not copied here.
